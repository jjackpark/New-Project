사용자 지시로 순서를 되돌렸다: 서버 PC/사내 백신 실측이 이 세션에서 불가능한 상태로 T002를 계속 막아두는 대신, **먼저 실제 프로그램(T002 스캐폴딩 이후)을 진행하고 T007의 남은 검증(서버 PC 더블클릭, 백신 반응)은 나중에 다시 다룬다.** 의존성을 원래대로 되돌려(T002는 T001에만 의존, T007은 T002 이후) priority를 `critical` → `low`로, 태그에 `deferred`를 추가했다. PACKAGING.md의 검증 결과(메커니즘 자체는 PASS)는 그대로 유효하며, 남은 미검증 항목(C1/I3/I4)은 실제 스캐폴딩된 코드가 나온 뒤 재검토한다.

### 검증 결과 (v2, 리뷰 반영 완료)

전체 결과와 근거는 **[PACKAGING.md](../PACKAGING.md)** 참고. 요약:

- esbuild 다중모듈 번들 → SEA exe 패키징 **성공** (외부 curl 요청으로 DB값+바이너리 해시 일치 확인, 음성 대조군은 정상적으로 FAIL)
- postject 주입 후 서명은 "손상"이 아니라 **완전 무서명**으로 정리됨(리뷰 예측을 실측으로 정정)
- WAL 모드 + 강제종료(`taskkill /F`) 후 재기동 시 **데이터 영속성 확인**
- 콜드 스타트 ~310~335ms, exe 크기 88.4MiB(zip 33MiB — 메일 첨부 한도 초과), `NODE_OPTIONS` 튜닝 가능 확인
- **새로 발견**: MOTW(다운로드 표시) 붙은 exe는 비대화형 실행 시 Windows가 자동 취소함 — exe 배포 채널(메일/다운로드 금지, USB·인트라넷 공유 권장)을 T002/배포 문서에서 정해야 함

**리뷰 과정**: opus 서브에이전트가 초안(v1) 계획의 치명적 결함 6건을 지적(핵심: 개발 PC 검증으로는 "서버 PC 더블클릭"이라는 요구사항 자체를 증명 못함, self-test가 자기인증이라 위양성 가능, 손으로 쓴 단일 파일이라 T002가 실제 쓸 esbuild 번들 파이프라인을 검증 안 함 등). C5(esbuild 파이프라인), C6(버전 고정·재현성), C3(외부 검증+음성대조군), C4(서버 상주형 self-test 폐기)는 전부 반영해 재실행했다. **C1(실제 서버 PC 검증)과 I3(백신 실반응)는 이 세션에 서버 PC/관리자 권한이 없어 검증 불가 — PACKAGING.md에 명시적 미검증 항목으로 남기고 T002 착수 전 사용자에게 별도 보고함.**

### 쉬운 설명

Node.js 앱을 Windows exe 파일 하나로 패키징하는 기술(Node SEA)을 실제 환경에서 검증하는 작업이다. 설치 과정 없이 더블클릭으로 실행되는 exe가 사내 환경(백신, 방화벽 등)에서 정상 동작하는지, 파일 크기가 합리적인 수준인지, 그리고 성능이 만족스러운지 확인하는 것이 목표다. 이 검증 결과는 프로젝트 스캐폴딩(T002)과 그 이후 작업들이 진행되기 위한 필수 전제이다.
