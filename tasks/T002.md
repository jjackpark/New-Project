### 구현 결과 (v2, 리뷰 반영 완료)

레포 구조: `package.json`(루트, 훅이 여기만 봄), `.nvmrc`/`.npmrc`(engine-strict), `eslint.config.js`(flat config), `.prettierignore`, `src/`(index.js, db.js, paths.js, assets.js, router.js — 전부 300줄 미만), `web/`(index.html, logo.png placeholder), `migrations/README.md`(T003용 자리), `scripts/bundle.js`(빠른 esbuild 번들, `npm run build`), `scripts/package-exe.js`(전체 SEA/postject 패키징, `npm run package`, 수동 실행 전용).

**실제로 실행해서 확인**(자기신고 아님): `npm run lint`/`npm run build` 그린, `npm start`(dev, 자산은 파일시스템 폴백)로 HTML+바이너리 자산 응답 확인, `npm run package`로 만든 실제 exe를 별도 폴더에서 실행해 curl로 HTML/바이너리 해시 일치까지 재확인(T007과 동일한 외부 검증 방식).

**리뷰 과정**: opus가 초안(v1)에서 치명적 6건을 지적 — 이번엔 그중 3건이 실행 중 그대로 재현됐다: (1) eslint sourceType 미분리로 `scripts/dashboard/public/js/*`(ESM)가 파싱 에러 날 뻔함 → flat config를 CJS 기본 + 대시보드만 예외로 재작성, (2) `dist/`가 eslint 대상에 걸릴 뻔함 → ignores 추가, (3) **"build"를 exe 전체 패키징으로 잡으면 Stop 훅이 92MB 빌드를 매 턴 반복해 턴 종료 자체가 막힌다** → `build`(빠른 번들)와 `package`(수동 exe 패키징)를 분리. 그 외 postject를 프로그래매틱 API로 호출(경로 공백 문제 회피), 버전 전부 고정 + package-lock.json 커밋, 데이터 경로를 `src/paths.js` 한 곳으로 통일(동기화 폴더 감지 포함), `assets.js`를 SEA/dev 이중 모드로 작성(exe 없이도 `npm start`로 화면 확인 가능 — T005가 여기 막히지 않게), 자산 매니페스트 자동 생성 + 기동 시 자가 점검. **직접 실행하다 발견한 별도 버그**: 자산 키를 `web/index.html`로 만들어 실제로 `ERR_SINGLE_EXECUTABLE_APPLICATION_ASSET_NOT_FOUND`가 났음 — 리뷰 지적이 아니라 실측 중 발견, 즉시 수정. 포맷터(prettier) 도입 시 기존 파일 전체가 걸리는 문제(I6)도 실제로 재현되어 `.prettierignore`로 이번 태스크 범위(`src/`, `web/`, 새 스크립트)만 포맷 대상으로 좁혔다.

**보류/사용자 확인 필요**: PACKAGING.md 권고 3(exe 배포 채널)은 ARCHITECTURE §9에 이미 기록됨. `useCodeCache`, better-sqlite3 대조는 T007처럼 범위 제외 유지.

### 쉬운 설명

Node.js 24.x LTS와 esbuild 번들링 + Node SEA exe 패키징 기술을 바탕으로 프로젝트 레포 구조를 초기화하는 작업이다. `package.json` 작성(린트 스크립트 포함), `.nvmrc` 고정, 빌드 파이프라인 구성(esbuild 다중모듈 번들 → SEA exe 생성)이 주요 내용이다. T001에서 기술 결정이 완료되었고, T007(exe 패키징 PoC)에서 기술적 가능성이 실증되었으므로, 이 작업은 그 결정들을 실제 코드·설정으로 구체화하는 단계다.
