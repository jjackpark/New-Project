## 작업 노트

### 프로세스 참고

이 태스크는 T005(레이아웃 셸)와 병렬로 fork에서 진행됐다. fork는 하드 룰상 서브에이전트(Agent 도구)를 추가로 못 띄우므로, 지금까지 써온 haiku(설명)+opus(비평) 병렬 서브에이전트 단계는 이번엔 생략하고 **직접 설계 → 자체 비평(아래 "직접 발견한 이슈") → 실제 실행 검증**으로 대체했다. backlog.json/git 커밋은 하지 않았다 — 부모가 두 fork 결과를 받은 뒤 순차 처리한다.

### 쉬운 설명

SPEC.md 5장에 나온 모든 데이터(프로젝트, 설비, 업체, 인력, 이슈, 알람, 일보, 사진 등)를 실제 테이블로 만들고, 앱이 켜질 때 자동으로 스키마를 적용해주는 마이그레이션 러너를 만드는 작업이다. 상태값(가동중/대기 등)은 자유 텍스트가 아니라 DB가 직접 걸러내도록 제약을 걸었다.

### 구현 결과

- `migrations/0001_core.sql`~`0004_reports_photos.sql`: SPEC §5.1의 15개 엔티티 전부(users, projects, role_options, vendors, equipment, personnel, master_plan_items/entries, qual_items, qual_runs, issues, alarms, daily_reports, daily_report_vendor_counts, photos). 상태값은 전부 `CHECK (... IN (...))`로 SPEC §5.5 허용값만 강제. FK는 §5.3 관계대로(Project→Equipment/Vendor/RoleOptions, Vendor→Personnel, Equipment→Personnel 선택). 날짜는 TEXT `YYYY-MM-DD`로 결정(ARCHITECTURE §S3가 미정으로 남겼던 것 — 여기서 확정).
- `src/migrate.js`: `PRAGMA user_version` 기반 순차 러너. **`src/assets.js`와 같은 SEA/dev 이중 모드**로 짰다 — 마이그레이션 파일을 SEA exe 안에서는 `node:sea` 자산으로, dev에서는 파일시스템으로 읽는다(migrations/README.md가 요구한 그대로).
- `src/index.js`에 `runMigrations()` 호출을 연결했다(기존엔 `openDb`만 하고 실제로 스키마를 적용하지 않고 있었음 — 이것도 스캐폴딩 단계의 미완성 부분이라 이번에 마저 채움).

**실제로 실행해서 확인**(자기신고 아님):
- 임시 DB에 마이그레이션 1차 적용 → 15개 테이블 전부 생성 확인, `user_version=4`.
- 동일 DB에 2차 적용 → 적용 파일 0건(멱등성 확인).
- 정상 삽입(project→vendor→equipment→personnel→issue→daily_report+vendor_count) 성공.
- CHECK 위반(잘못된 status), FK 위반(존재하지 않는 vendor_id), 길이 제약 위반(설비명 12자 초과), UNIQUE 위반(같은 설비·날짜 일보 중복) 4종 전부 정상 거부됨을 직접 확인.
- `SM_DATA_DIR`/`SM_PORT` 지정해 실제로 `node src/index.js` 기동 → "적용된 마이그레이션: ..." 로그와 함께 실제 DB 파일에 15개 테이블 생성 확인.
- `npx eslint`/`npx prettier --check`를 내 파일(src/migrate.js, src/db.js, src/index.js, src/paths.js)에 한해 개별 실행해 그린 확인 — **전역 `npm run lint`는 T005 fork가 동시에 web/router.js를 고치는 중이라 그쪽 파일 때문에 일시적으로 빨간불이었음(내 책임 범위 아님, 아래 참고).**
- 시간 제약상 패키징된 exe(`npm run package`)로의 전체 재검증은 하지 않았다 — T005와 동시에 소스가 바뀌는 중이라 지금 실행하면 어느 쪽 변경 때문인지 분간이 안 된다. **두 fork가 합쳐진 뒤 전체 파이프라인(lint+build+package) 한 번 더 확인 필요.**

### 직접 발견한 이슈 (서브에이전트 비평 대신 자체 검토)

1. **순환 FK 초안 실수**: equipment.담당자를 personnel FK로 설계했다가 personnel.equipment_id와 순환 참조가 됨을 발견 — SPEC §5.4를 다시 읽어보니 "인력 목록에서 선택" 권장은 이슈/Qual/마스터플랜/알람에만 해당하고 설비 자체는 언급이 없어서, equipment.담당자는 자유텍스트로 되돌렸다. **확인 필요**: 이 해석이 틀렸다면(즉 설비 담당자도 personnel 선택이어야 한다면) 순환 FK를 다른 방식(예: 담당자 이력을 별도 테이블로 분리)으로 다시 풀어야 한다.
2. **dailyReports 세분성**: SPEC 5.1 표는 dailyReports에 "설비" 필드가 있다고 하고 5.3 관계도는 `DailyReport(Project, 날짜) 1─N (Vendor, 인원수)`라고 해서 두 서술이 살짝 다르다. `daily_reports`(설비+날짜 단위, UNIQUE)와 `daily_report_vendor_counts`(프로젝트+날짜 단위, 설비 무관)를 분리해서 둘 다 만족하게 했다.
3. **masterPlanEntries**를 item_id에 대해 1:1(UNIQUE)로 모델링했다 — SPEC이 "항목별 실적"이라고만 해서 이력(여러 번 갱신)이 아니라 현재 상태 1건으로 해석했다. 이력이 필요하면 나중에 UNIQUE를 풀고 정렬 컬럼을 추가해야 한다.
4. **role_options 초기값(PM/리더/설계/전장/공정/제어/PLC)**은 마이그레이션에 넣지 않았다 — project_id가 NOT NULL이라 프로젝트가 생기기 전에는 시드할 수 없다. 프로젝트 생성 로직(T010 등)에서 채워야 한다.
5. **`src/index.js`가 아직 실제 라우트에서 db를 안 쓴다** — 스키마와 마이그레이션만 이 태스크 범위이고, 화면별 CRUD는 이후 태스크(1-core-data phase)에서 연결한다.
